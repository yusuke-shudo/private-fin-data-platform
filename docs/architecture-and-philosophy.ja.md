# private-fin-data-platform: 設計思想とアーキテクチャ

- English version: [architecture-and-philosophy.md](architecture-and-philosophy.md)

## 1. 位置づけ

このリポジトリは、AWS と Snowflake 上で構成する個人向け金融データ基盤の、実運用を意識した実装例である。

ワンクリックで使えるテンプレートを目的にはしていない。
目的は、設計の責務境界を明示し、運用を再現可能にし、現実の制約下でのトレードオフを記録することにある。

## 2. 設計の中核原則

### 2.1 責務境界を明確にする

- Terraform はプラットフォーム/インフラ資源を管理する。
- schemachange は SQL マイグレーション資産を管理する。
- dbt は変換と分析モデリングを管理する。

各レイヤは 1 つの主責務を持ち、結合とレビュー曖昧性を抑える。

### 2.2 便利さより再現性

- 同じ変更は、誰が実行しても同じ結果になることを優先する。
- 環境差分は環境ごとの設定で明示的に制御する。
- CI の実行定義はリポジトリでバージョン管理する。

### 2.3 暗黙自動化より明示運用

- 初期 bootstrap は one-time の手作業として記録する。
- 継続運用は bootstrap と分離する。
- 実行順序は文書化し、決定論的に保つ。

### 2.4 コストを一次制約として扱う

- 小規模な個人運用を前提に設計する。
- 不要な前処理計算より、ストレージ優先の受け入れを選ぶ。

## 3. 環境戦略

### 3.1 現状と拡張前提

- 現時点の基準環境は dev と prd の 2 つ。
- 将来的な stg などの追加を許容する。

Terraform と schemachange は既に環境分離ディレクトリ構成のため、環境追加は既存パターンの拡張として扱える。

### 3.2 ブランチ戦略への含意

- インフラとマイグレーション資産は、main 中心の GitHub Flow を基本とする。
- 環境数が増えると、dbt は main 中心運用だけでは検証負荷が高まる可能性がある。
- 必要に応じて、dbt に Git Flow 的な段階運用を導入する余地を残す。

## 4. リポジトリ構成と承認境界

AWS と Snowflake は現在 1 つのリポジトリで管理する。

- 承認境界は CODEOWNERS で表現する。
- 組織境界や政治的制約で承認責任が分断される場合がある。
- CODEOWNERS で運用が成立しない場合、リポジトリ分割は正当な選択肢とする。

重要なのは monorepo の純度ではなく、レビュー責任とリリース責任の明確性である。

## 5. AWS 設計方針

### 5.1 推奨モデル（マルチアカウント）

1. dev 用 OU と prd 用 OU を手作業で作成する。
2. 同一テンプレートを両 OU に適用する。
3. テンプレートで Terraform 実行基盤を準備する。
	- tfstate 保存用 S3
	- GitHub Actions 用 S3 Access Point
	- アクセス経路制御用 IAM ロール

IAM ロール本体は最小化し、アクセス制御は Access Point ポリシー側で担保する。

### 5.2 アクセスモデル

- 人のログインユーザは組織アカウント側で管理し、SSO を前提とする。

### 5.3 組織アカウントを使えない場合の代替

- ユーザ管理兼 StackSets 管理アカウントを用意する。
- 各アカウントへは switch-role で入る。
- ベースライン構築は StackSets を使う。

### 5.4 単一アカウント制約（非推奨）

AWS が 1 アカウントしか使えない場合:

- 環境識別を命名規約で強制する。
- dev/prd 用ロールを明確に分離する。
- コスト按分をタグ等で厳格に運用する。

運用は可能だが、事故リスクとガバナンス負荷が上がる。

## 6. Snowflake 設計方針

### 6.1 Datalake 方針

データはまず Snowflake に集約する方針を採る。

- Snowflake を主たる Datalake 基盤として扱う。
- コストが許す限り、生データを生のまま受け入れて保持する。
- データ提供元には、提供のためだけの個別 ETL を極力要求しない。

### 6.2 DB/スキーマの層構造

- DATALAKE_DB: 生データ取り込み層（Bronze）
- DATAWAREHOUSE_DB: 標準化・整形層（Silver）
- DATAMART_DB: 利用者向け提供層

DATALAKE_DB 配下はデータソース単位でスキーマ分割する。

### 6.3 標準化の方針

- 標準化は STAGING から始める。
- カラム名揺れ、意味揺れ、構造不一致は可能な限り早い段階で吸収する。
- STAGING では複数テーブル結合を避け、形状整備を主目的とする。

### 6.4 Core と配布方針

- CORE は下流分析と AI 活用を見据えて設計する。
- CORE は可能な範囲で Iceberg 形式でも提供する。
- これにより、Snowflake 直接利用が前提でない利用者にも S3 経由の利用経路を提供する。

### 6.5 アカウント戦略

推奨モデル:

- dev/prd の Snowflake アカウントを手作業で分離作成する。
- 各アカウント内で、用途別（基盤運用/データ活用）にロール・ユーザ・ウェアハウスを分離する。

代替モデル（単一アカウントのみ利用可能な場合）:

- DB、ロール、ウェアハウス、サービスユーザを環境接尾辞で分離する。

## 7. 運用モデル

### 7.1 Bootstrap と継続運用の分離

- bootstrap は one-time の手動初期化とする。
- 以後の継続変更は Terraform と schemachange で管理する。

### 7.2 TASK 運用方針

- TASK 定義はマイグレーション資産として管理する。
- TASK 再定義後の自動 RESUME は意図的に行わない。
- 実行権限と所有権境界は、対象オブジェクトに近い場所で明示管理する。

## 8. セキュリティと公開方針

- 本リポジトリは設計透明性のための public repository である。
- シークレットをソース管理に保存しない。
- 実行時認証は workload identity と環境設定による注入を前提とする。
- ここで示すのは実装パターンであり、組織全体の信頼ポリシー定義そのものではない。

## 9. トレードオフ

- 1 リポジトリ運用は全体追跡性を高めるが、レビュー責任境界が複雑化しうる。
- main 中心運用はインフラ/マイグレーションでは効率的だが、dbt では将来不足する可能性がある。
- 単一アカウント代替案は現実的だが、運用リスクが高い。

## 10. 非目標

- すべての企業ガバナンス要件をこのリポジトリで網羅すること。
- すべての組織に通用する唯一の標準運用を規定すること。
- 初期段階から厳密なドメイン分割を必須化すること。

## 11. 今後の拡張方向

想定する次の拡張:

- stg 追加時の Terraform/schemachange/workflow 拡張規約の明文化
- dbt のブランチ戦略を main 中心から発展させる判断基準の明文化
- マスキング等のガバナンス資産拡充
- 非 Snowflake 利用者向け Iceberg 提供契約の強化

基本方針は一貫している。運用価値が明確な場合にのみ複雑性を追加する。

# private-fin-data-platform: 設計思想とアーキテクチャ

- English version: [architecture-and-philosophy.md](architecture-and-philosophy.md)

## 1. このシステムが目指すもの

このリポジトリは、AWS、Snowflake、GitHub Actions を用いた個人向け金融データプラットフォームの参照実装である。

目的は、ワンクリックで本番投入できるテンプレートを提供することではない。目的は、設計判断を明示化し、再利用可能にすることである。

- インフラ、スキーマ変更、変換ロジックの責務をどう分離するか
- デプロイをどう再現可能・可観測にするか
- 個人運用のコスト制約の中で、商用品質の設計規律をどう維持するか

特別な制約がない限り、自分が最善だと思う設計・実装を採用している。つまり、一般的なテンプレートというより、実際に動く形の実例として読むのが適している。

具体例は次のとおりである。

- AWS と Snowflake の双方で Organization の機能を利用し、`dev` と `prd` を別アカウントとして分離している。
	特に Snowflake では、企業によっては開発環境と本番環境を同一アカウントで運用するケースも多いため、本リポジトリではより厳格な分離モデルを採用している。
- Terraform では、`snowflake_stage_resource` や `snowflake_storage_integration_aws_resource` のような Snowflake provider の preview 機能を使っている。
- AWS と Snowflake の構築処理は 1 つの monorepo に同居しており、変更箇所に応じて AWS 管理者または Snowflake 管理者のいずれかが承認責任を持つ形になっている。
- 既定の CI/CD は `main` ブランチへの PR を起点にした DEV 自動化であり、`dev` や `next` のようなブランチ運用は想定していない。
- Snowflake への取り込み先は意図的に `DATALAKE_DB` に集約している。
- raw の datalake テーブルは、ELT 前提で基本的に 4 カラム構成（`ingest_at`, `file_path`, `line_number`, `raw_payload`）の単純な形を採っている。

## 2. 設計原則

### 2.1 責務分離

- Terraform はインフラとプラットフォーム資源を管理する。
- schemachange は DDL として管理すべき SQL マイグレーションを扱う。
- dbt は変換ロジックと分析モデルを管理する。

各レイヤに主責務を明確に割り当てることで、隠れた結合とレビュー複雑性を下げる。

### 2.2 便利さより再現性

同じ操作を誰が実行しても同じ結果になることを重視する。

- 環境差分は環境変数で注入する。
- CI ワークフローはコードとして管理し、実行を定義化する。
- マイグレーション履歴は永続化し、監査可能にする。

### 2.3 安全側に倒すリリース設計

取り返しのつかない変更の前に、明示的な検証を通す設計を採用する。

- Pull Request でインフラ・マイグレーション変更を検証する。
- 本番ワークフローでは検証と反映を分離する。
- 依存関係を満たす実行順序を固定し、失敗時の解釈を容易にする。

### 2.4 コストを設計制約として扱う

個人利用では、コスト管理を後付けではなく設計制約として扱う。

- 小さな既定コンピュートサイズ
- 短時間実行を前提とした運用
- 必要に応じて手動・低頻度実行を選ぶ

## 3. アーキテクチャ全体像

全体は control plane と data plane に分けて考える。

- Control plane: GitHub リポジトリ、CI ワークフロー、Terraform、schemachange、dbt 実行
- Data plane: S3 ランディング、Snowflake の DB/Schema/Table、分析用モデル

この分離により、デプロイ機構とビジネスデータモデリングを独立して進化させられる。

## 4. データライフサイクル

データ処理はレイヤ構造で運用する。

1. 生ファイルを datalake raw テーブルへ取り込む
2. datawarehouse で正規化・モデル化する
3. datamart で分析向けの提供形に仕上げる

raw 取り込みは append 固定ではなく、データ特性に応じて append / 全件入れ替え / スライス単位の再取込（DELETE+INSERT または MERGE）を使い分ける。
特定口座譲渡損益履歴のような年次ファイルでは、`year` をスライスキーとして対象年のみを再構築する。

## 5. Terraform + schemachange + dbt を併用する理由

この3つは重複ではなく、境界を持って併用する。

- Terraform: アカウント/DB/Schema レベルのインフラと統合資源
- schemachange: DB オブジェクト進化のための SQL マイグレーション
- dbt: モデル系統管理、テスト、変換オーケストレーション

実務上の境界として、プラットフォーム側の変更は dbt に寄せず、分析ロジックはインフラコードに混ぜない。

## 6. 信頼性と運用性

運用の信頼性は、複雑な仕組みより明示的なパターンで担保する。

- 依存を満たす順序実行
- dev/prd の環境分離
- ワークフロー定義のバージョン管理
- change history table による追跡性

現在のワークフロー設計は、承認の連続回数を抑えつつ、順序保証を維持する方針である。

## 7. セキュリティとガバナンスの前提

本リポジトリは公開リポジトリであり、設計透明性を重視している。

- 収録データはサンプルのみ
- シークレットはリポジトリに保存しない
- 実行時認証は workload identity と環境設定で注入する前提

ここで示すのは組織ポリシーそのものではなく、実装パターンである。

## 8. トレードオフと非目標

### トレードオフ

- シンプルなワークフローは運用負荷を下げる一方、ステップ分離は弱くなる。
- 個人運用でのコスト最適化は、完全自動化より手動実行を選ぶ場合がある。
- 公開可読性を重視すると、組織固有制御の詳細は取り込みにくい。

### 非目標

- あらゆる企業ガバナンス要件をこのリポジトリ単体で網羅すること。
- すべての組織に共通する唯一の運用モデルを規定すること。

## 9. 今後の方向性

拡張候補は次の通り。

- 必要に応じたドメイン/DB単位のワークフロー細分化
- dbt では扱いにくい領域（masking、row access など）のポリシー管理拡充
- serverless 利用量可視化を含むコストガード強化

基本方針は一貫している。運用価値が明確なときだけ複雑性を追加する。
